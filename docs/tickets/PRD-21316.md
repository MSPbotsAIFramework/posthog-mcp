## Product design

### Goals / Non-goals

**Goals (v1):**
- Give agent-platform users read access to the PostHog data a team would actually ask an AI assistant about: feature flags, insights (saved analyses/charts), raw events, persons, cohorts, and annotations.
- Support PostHog's three hosting regions (US Cloud, EU Cloud, self-hosted) through one connector, since the ticket names no specific region and PostHog's own docs treat region as a hard routing requirement, not an edge case.
- Keep every tool read-only (`readOnlyHint: true`) — the ticket states no destructive or write requirement, and introducing write/delete tools (e.g. toggling a feature flag that controls a live product rollout) is a materially different risk profile that would need its own explicit ask.

**Non-goals (v1, follow-up candidates — see "Scope split"):**
- No write/mutate tools (create/update feature flags, insights, annotations, cohorts). Nothing in the ticket asks for this, and PostHog feature flags gate live product behavior — enabling blind writes without a stated use case is a business-risk decision, not an implementation detail.
- No session replay, experiments, dashboards, data warehouse, or LLM-observability (traces) tool groups. These are large, separate areas of the PostHog API (dashboards alone is 25 endpoints) with their own object models; bundling them into v1 would roughly double scope for capabilities nobody asked for.
- No ad-hoc HogQL query execution tool (`/api/projects/{project_id}/query/`). It is a read endpoint, but it accepts an arbitrary analytics query language — exposing it as a generic "run this query" tool is a different, larger design question (what HogQL subset is safe to expose to an LLM-driven caller) than this ticket's ask.
- No local feature-flag evaluation (client-side flag evaluation libraries) — v1 only reads flag *definitions* via the server API, it does not evaluate flags for a given user.

### Acceptance criteria AC1..AC13

- **AC1**: Given a valid `X-PostHog-Api-Key` and `X-PostHog-Project-Id`, When the agent calls the list-feature-flags tool, Then it returns that project's feature flags (key, name, active, archived, filters) with pagination metadata (`has_more`, next offset).
- **AC2**: Given a feature flag id that exists in the project, When the agent calls get-feature-flag, Then it returns that flag's full definition including its rollout filters.
- **AC3**: Given a feature flag id that does not exist (or belongs to a different project), When get-feature-flag is called, Then the tool returns a structured `not_found` error, not a raw 404 passthrough or a crash.
- **AC4**: Given valid credentials, When list-insights is called without asking for full chart data, Then it returns insight metadata (name, short_id, description, filters) without the (potentially large) `result` chart-data payload.
- **AC5**: Given an existing insight id, When get-insight is called with `include_result=true`, Then it returns that insight's `result` data in addition to its metadata, truncated per the token-economy rule if it exceeds the response size cap.
- **AC6**: Given event filters (event name, distinct_id, time range), When list-events is called, Then only matching events are returned, newest-first, up to the requested limit.
- **AC7**: Given a search term (email, name, or distinct id fragment), When list-persons is called, Then matching persons are returned.
- **AC8**: Given a person id, When get-person is called, Then that person's profile (distinct_ids, properties) is returned.
- **AC9**: Given a list tool is called with filters that match nothing, When the vendor API returns zero results, Then the tool returns an empty array (`[]`), not an error and not `null`.
- **AC10**: Given `X-PostHog-Api-Key` or `X-PostHog-Project-Id` is missing, When any tool is called, Then the tool returns 401 with a body naming the missing header(s) — not a 500, and not a silent fallback to any default credential.
- **AC11 (multi-tenant isolation)**: Given two requests carrying two different tenants' PostHog credentials and project ids, When both call the same tool concurrently, Then each request's response reflects only its own project's data — no credential or response data crosses between the two requests.
- **AC12 (region routing)**: Given `X-PostHog-Host` is not supplied, When any tool is called, Then requests go to PostHog's US Cloud default (`https://us.posthog.com`); given `X-PostHog-Host` is supplied (EU Cloud or a self-hosted domain), Then requests go to that host instead.
- **AC13 (rate limiting)**: Given PostHog responds with `429 Too Many Requests`, When a tool call hits it, Then the tool retries with backoff honoring the vendor's `Retry-After` header up to the configured retry budget, and surfaces a structured `rate_limited` error if the budget is exhausted — it does not fail the caller's request on the first 429.

### Open questions

- [non-blocking] Should v1 include a write tool for creating annotations (a low-risk, additive, non-destructive write — annotations are just timestamped notes on a chart, not a behavior-changing object like a feature flag)? Defaulted to **not in v1** per the SOP's "default read-only, write needs justification" rule (A4); easy to add in a follow-up ticket if requested, see "Scope split".
- [assumed] Assumed the connector only needs to support a single PostHog project per credential set (one `X-PostHog-Project-Id` per connection), matching how every other MSPbots connector in this org binds one set of headers to one upstream account/tenant. If a user needs to query multiple PostHog projects from one agent session, that would need a per-call project override, which section "Non-goals" explicitly avoided for isolation reasons — if this assumption is wrong, section "Data & API contract" needs rework.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/posthog-mcp` from scratch (main line A, Python 3.12 + uv + FastMCP, per the vendor-mcp-development SOP) as a stateless Streamable-HTTP MCP server with 9 read-only tools covering feature flags, insights, events, persons, cohorts, and annotations. Credentials (API key, project id, optional host) are read per-request from headers via a `contextvars.ContextVar`-scoped HTTP client wrapper — no new mechanism beyond what every other vendor-mcp repo in this org already does. This is the cheapest way to deliver the ask because PostHog's REST API is a single, well-documented surface (public OpenAPI schema) with no OAuth dance for the capabilities in scope — a Personal API Key is sufficient.

### Data & API contract

**Credential headers** (read by `middleware.py`, forwarded nowhere except into the outbound PostHog request):

| Header | Required | Type | Used for |
|---|---|---|---|
| `X-PostHog-Api-Key` | Yes | password | Sent upstream as `Authorization: Bearer <key>` on every PostHog API call (PostHog Personal API Key) |
| `X-PostHog-Project-Id` | Yes | str | Substituted into every `/api/projects/{project_id}/...` path; never accepted as a tool argument (see tech design AC11 rationale) |
| `X-PostHog-Host` | No (default `https://us.posthog.com`) | str | Base URL for EU Cloud (`https://eu.posthog.com`) or a self-hosted instance's own domain |

`credential_fields` payload for `mcppub register` (dev leg, recorded here so the design and the eventual registration call agree on field names):

```json
{
  "X-PostHog-Api-Key": {"label": "Personal API Key", "type": "password", "required": true,
    "description": "PostHog Personal API key (Settings -> Personal API keys)", "example": "phx_xxx"},
  "X-PostHog-Project-Id": {"label": "Project ID", "type": "str", "required": true,
    "description": "Numeric PostHog Project ID (Project Settings -> Project ID)", "example": "12345"},
  "X-PostHog-Host": {"label": "API Host", "type": "str", "required": false,
    "description": "PostHog API host for EU Cloud or self-hosted; default https://us.posthog.com",
    "example": "https://eu.posthog.com"}
}
```

**Tools (9, all `readOnlyHint: true`)** — request params are options-shaped; responses are compact JSON (`ensure_ascii=False`, no `indent=2`), lists capped at `limit` (default 20, hard max 100) with `has_more` computed from PostHog's `next` field:

| Tool | Upstream endpoint | Key params | Notes |
|---|---|---|---|
| `posthog_list_feature_flags` | `GET /api/projects/{project_id}/feature_flags/` | `key?`, `search?`, `active?`, `archived?`, `limit`, `offset` | |
| `posthog_get_feature_flag` | `GET /api/projects/{project_id}/feature_flags/{id}/` | `id` | 404 -> `not_found` |
| `posthog_list_insights` | `GET /api/projects/{project_id}/insights/?basic=true` | `search?`, `saved?`, `favorited?`, `tags?`, `limit`, `offset` | `basic=true` always, to omit the (potentially large) `result` field — see AC4 |
| `posthog_get_insight` | `GET /api/projects/{project_id}/insights/{id}/` | `id`, `include_result` (default `false`) | `include_result=true` fetches without `basic=true`; `result` truncated if the serialized response would exceed ~20000 chars |
| `posthog_list_events` | `GET /api/projects/{project_id}/events/` | `event?`, `distinct_id?`, `person_id?`, `after?`, `before?`, `limit`, `offset` | `limit` hard-capped at 100 (vendor default page is large; this keeps responses token-cheap) |
| `posthog_list_persons` | `GET /api/projects/{project_id}/persons/` | `search?`, `email?`, `distinct_id?`, `limit`, `offset` | |
| `posthog_get_person` | `GET /api/projects/{project_id}/persons/{id}/` | `id` | 404 -> `not_found` |
| `posthog_list_cohorts` | `GET /api/projects/{project_id}/cohorts/` | `search?`, `type?` (`static`/`dynamic`), `limit`, `offset` | |
| `posthog_list_annotations` | `GET /api/projects/{project_id}/annotations/` | `search?`, `limit`, `offset` | |

**Error envelope** (all tools, on any upstream failure): `{"error": {"code": "...", "message": "...", "retryable": bool}}`. Mapping: vendor 401/403 -> `unauthorized`; 404 -> `not_found`; 400 -> `invalid_argument`; 429 -> `rate_limited` (`retryable: true`) after the retry budget is exhausted; 5xx -> `upstream_error` (`retryable: true`). Missing required header (local check, before any outbound call) -> HTTP 401 with a body naming the missing header(s), per SOP §3.2.

**Backward compatibility**: not applicable — first version of a new connector, nothing to be compatible with.

### Key flow / sequence

```
Agent -> Gateway -> posthog-mcp /mcp (tools/call: posthog_list_feature_flags)
  posthog-mcp: read X-PostHog-Api-Key / X-PostHog-Project-Id / X-PostHog-Host from request headers
            -> set ContextVar for this request
            -> httpx GET {host}/api/projects/{project_id}/feature_flags/?limit=20
                 Authorization: Bearer {api_key}
            -> on 200: trim fields, compute has_more from `next`, return JSON string
            -> on 401/403/404/400/429/5xx: map to structured error envelope
            -> finally: reset ContextVar
  posthog-mcp -> Gateway -> Agent
```

### Non-functional

- **Idempotency & concurrency**: every tool is a GET against PostHog, inherently idempotent; no local state is written, so concurrent calls for different tenants never interact (AC11). Concurrency correctness rests entirely on the `ContextVar` + `finally: reset()` pattern — tested directly in `tests/test_middleware.py`.
- **Performance**: PostHog's own published limits — analytics-style endpoints (events) 240/min & 1200/hour, query 2400/hour, feature-flag/prompt endpoints 600/min, standard CRUD (persons/cohorts/annotations/insights list+get) 480/min & 4800/hour. v1's read-only, on-demand call pattern (one upstream call per tool call, no polling) stays well under these for any plausible single-agent-session usage; no local rate-limiting is added beyond honoring `Retry-After` on 429 (AC13).
- **Security**: credentials never touch disk, env vars, or logs — read from the header, held only in the request-scoped `ContextVar`, forwarded only as the outbound `Authorization` header. Error messages never echo the API key back (only the vendor's own error `message` field, which does not contain the key). `gitleaks detect` run before delivery (SOP §11); no real PostHog credentials anywhere in the repo, examples use placeholders.
- **Multi-tenant isolation**: enforced structurally, not by convention — `project_id` is read only from the per-request header, never accepted as a tool argument (see AC11's Open-question rationale), so there is no code path by which one request's tool call can address another tenant's project.
- **Observability**: structured log line per tool call (tool name, HTTP status returned to caller, latency) with API key and raw response bodies excluded; `/health` returns `{"status": "ok"}` without calling PostHog, so health checks never depend on vendor uptime or burn vendor rate-limit budget.

### Risks & dependencies

- **Risk**: PostHog's rate limits (see "Non-functional") are per-organization, not per-connector — if the same PostHog org is also queried heavily through other integrations, this connector's calls share that budget. Mitigated by the retry/backoff on 429 (AC13); no further mitigation needed for a read-only, on-demand tool.
- **Risk**: `include_result=true` on `posthog_get_insight` can return large nested chart-data payloads for complex insights (e.g. funnels with many steps). Mitigated by the ~20000-char truncation rule already in the contract (same rule every other MCP in this org applies, SOP A4).
- **Dependency**: none on another ClickUp ticket or unmerged branch — this is a standalone new connector.
- **Dependency**: registration (`/api/vendor-register`) is a one-time event for this vendor; if it fails or needs re-running, every subsequent change goes through `/api/deploy-int` instead (standard for every vendor-mcp repo in this org, not specific to this ticket).

## Decisions made by DEV01

(Per `references/mcp-track.md` 2.4 — choices made without anyone to ask, posted as a separate ClickUp comment after the `[DESIGN]` stub.)

- Chose a **read-only tool set for v1** (9 tools, all `readOnlyHint: true`) — the ticket has no specific requirement beyond "connect PostHog"; alternative considered was including write endpoints for feature flags/insights/annotations, rejected because the SOP's default is read-only and no business justification for write access was stated in the ticket.
- Added an **optional `X-PostHog-Host` header** (default `https://us.posthog.com`) to support EU Cloud and self-hosted PostHog deployments — PostHog's own docs are explicit that region/host is a hard routing requirement, not an edge case; alternative was hardcoding the US Cloud host only, rejected because it would silently misroute (or simply fail to reach) EU Cloud or self-hosted tenants' data.
- **Project ID is a credential header, never a tool parameter** — alternative was accepting `project_id` as a tool argument (closer to how the raw PostHog API works), rejected because that would let a caller address a project outside the credential's authorized scope, undermining the per-request isolation guarantee (AC11).
- **`posthog_list_insights` defaults to `basic=true`** (metadata only, no `result` chart-data payload) unless the caller explicitly asks for full data via `posthog_get_insight(include_result=true)` — alternative was always returning full insight data including `result`, rejected for token economy; PostHog's own insight payloads can carry large nested chart-series data that would dominate a list response for no benefit in a "what insights exist" query.
- **Excluded session recordings, experiments, dashboards, and ad-hoc HogQL query execution from v1** — the ticket names no specific capability beyond generic "live access"; these are each large, separate sub-surfaces of PostHog's API (dashboards alone is 25 endpoints) and HogQL query execution in particular raises its own "what query shapes are safe to expose to an LLM-driven caller" design question that is bigger than this ticket's stated ask. Recorded as follow-up candidates in "Scope split" below.
- To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

## Scope split

MVP (this ticket) delivers the 9 read-only tools above. Later-iteration candidates, each independently useful and each its own follow-up ticket if requested:
- A low-risk write tool for creating annotations (additive, non-destructive — unlike feature-flag/insight writes, an annotation does not change product behavior).
- Session recordings (list/get metadata — not recording playback, which is a large separate feature).
- Experiments (list/get, read-only) — PostHog's experiments build on feature flags already covered in v1.
- A carefully-scoped, read-only HogQL query tool, once there is a stated need and a security review of what query shapes to allow.
